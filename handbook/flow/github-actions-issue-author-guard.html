GitHub Actions · Issue-Triggered Automation

辨識 Issue 開立者
與權限守門機制

Repo 開放 400+ 位協作者（多為外單位 read 角色），但只有約 10 位維護人員應能觸發後續帶 token 的 Claude 自動化流程。本手冊整理如何在 Actions 中辨識開 issue 的人、判斷其權限，並在呼叫 server 前擋下未授權者。

00問題情境

流程鏈是：有人建立 issue → 觸發 issues: opened workflow → workflow 用 vcalud 呼叫 server 上的 Claude 執行任務。

風險在於 issues: opened 這個事件，任何具有 read 權限的人都能觸發。若不加判斷，那 400 位外單位協作者都能驅動後面帶著 credential 的步驟。目標是在流程最前端辨識開立者身分，只放行約 10 位維護者。

01Payload 拿得到什麼

issues 事件的 payload 直接提供開立者的帳號與「關係層級」，但不會告訴你他屬於哪個 team。

欄位內容可用於
github.event.issue.user.login 開 issue 的 GitHub 帳號名 白名單比對、API 查詢的 key
github.event.issue.author_association 與 repo 的關係層級：OWNER / MEMBER / COLLABORATOR / CONTRIBUTOR / NONE 粗粒度分類（org member vs 外部）
關鍵限制

Payload 不含 team 資訊。要知道「他屬於哪個 team / 權限組」，一定要另外呼叫 GitHub API。

02author_association 的限制

author_association 告訴你的是「他是 org member 還是外部 collaborator」這種粗分類，而不是 team。

對本情境最致命的一點：它無法區分 read collaborator 和 write collaborator——兩者都回傳 COLLABORATOR。既然外單位 400 人和維護者可能都是 collaborator，這個欄位的區分度不足以當守門依據。

03三種辨識方法

方法 A：帳號白名單簡單

把約 10 位維護者帳號寫進 workflow 或 repo variable，完全比對。簡單但需手動維護；務必用完全比對，避免相近帳號名繞過。

方法 B：查權限等級推薦

呼叫 API 查開立者對 repo 的權限，read 直接擋、write / admin 放行。免維護名單，且比 author_association 準（能區分 read 與 write）。

方法 C：查 team 成員最乾淨

維護者放進一個 GitHub Team，workflow 動態查對方是否在 team 內。比對邏輯不寫死，但需一顆能讀 org/team 的 token。

方法 A — 帳號白名單

on:
  issues:
    types: [opened]

jobs:
  guard:
    runs-on: ubuntu-latest
    steps:
      - name: Check author
        env:
          ACTOR: ${{ github.event.issue.user.login }}
        run: |
          ALLOWED="william pedro samura steven oceanTsai"
          # 完全比對，勿用 grep pattern
          for u in $ALLOWED; do
            [ "$u" = "$ACTOR" ] && exit 0
          done
          echo "::error::$ACTOR is not authorized"
          exit 1

方法 B — 查權限等級

- name: Check permission
  env:
    GH_TOKEN: ${{ secrets.ORG_READ_TOKEN }}
    ACTOR: ${{ github.event.issue.user.login }}
  run: |
    perm=$(gh api \
      "repos/YOUR_ORG/YOUR_REPO/collaborators/$ACTOR/permission" \
      --jq '.permission')
    # 回 admin / write / read / none
    if [ "$perm" = "read" ] || [ "$perm" = "none" ]; then
      echo "::error::$ACTOR has only $perm"
      exit 1
    fi

方法 C — 查 team 成員

- name: Check team membership
  env:
    GH_TOKEN: ${{ secrets.ORG_READ_TOKEN }}
    ACTOR: ${{ github.event.issue.user.login }}
  run: |
    status=$(gh api \
      "orgs/YOUR_ORG/teams/b-team/memberships/$ACTOR" \
      --jq '.state' 2>/dev/null || echo "none")
    # active = 在 team；404 = 不在
    if [ "$status" != "active" ]; then
      echo "::error::$ACTOR not in b-team"
      exit 1
    fi

04Gatekeeper 完整範例

把守門獨立成一個 job，後續呼叫 Claude 的 job 用 needs: 相依。未通過就整條中斷，未授權者的 issue 內容永遠流不進帶 token 的步驟。

on:
  issues:
    types: [opened]

jobs:
  # ---- 第一關：守門 ----
  guard:
    runs-on: ubuntu-latest
    steps:
      - name: Authorize by permission
        env:
          GH_TOKEN: ${{ secrets.ORG_READ_TOKEN }}
          ACTOR: ${{ github.event.issue.user.login }}
        run: |
          perm=$(gh api \
            "repos/${{ github.repository }}/collaborators/$ACTOR/permission" \
            --jq '.permission')
          case "$perm" in
            admin|write) echo "authorized ($perm)" ;;
            *) echo "::error::$ACTOR: $perm"; exit 1 ;;
          esac

  # ---- 第二關：確認通過才呼叫 Claude ----
  run-claude:
    needs: guard
    runs-on: ubuntu-latest
    steps:
      - name: Call server via vcalud
        run: |
          # issue 內容於此才進入流程
          # 仍須做 injection 防護（見下節）
          ...

05安全硬化要點

守門要在最前端

Gatekeeper 必須是呼叫 Claude 之前的第一個 job，後續 job 以 needs: 相依。別讓未授權者的 issue 內容先流進帶 credential 的步驟才判斷。

Injection 防護不可省

issue 的 title / body 之後若拼進 shell 或傳給 Claude，仍要照 Jira sync 那套做 injection 防護——因為授權者也可能貼進惡意內容。用 env 變數傳值、避免直接內插到 run: 字串。

白名單用完全比對

若採方法 A，用 [ "$u" = "$ACTOR" ] 完全比對，不要用 grep pattern，避免有人取相近帳號名繞過。

06選型建議

以 400 人規模、名單會變動來說：

最省事：既然外單位全是 read、維護者是 write 以上，直接用方法 B（查權限），read 就擋掉，連 team 名單都不用維護，也比 author_association 準。

最乾淨、最好維護：方法 C（查 team）。維護者集中在一個專用 GitHub Team，人員異動只需調整 team 成員，workflow 不動。若目前維護者尚未集中在某個 team，建議建一個專門給這條 automation 用。

結論

兩者皆需一顆能讀 org 的 token。若不想維護名單、且維護者權限已與外單位明確分層 → 方法 B。若希望邏輯完全不寫死、可長期擴充 → 方法 C。
