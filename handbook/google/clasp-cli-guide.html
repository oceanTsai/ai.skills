用 clasp 在本機開發
Google Apps Script

把 GAS 從瀏覽器編輯器搬回你的 VS Code、Git 與 CI，涵蓋獨立與試算表綁定兩種型態。

clasp 是什麼

clasp（Command Line Apps Script Projects）是 Google 官方的 GAS 命令列工具，讓你在本機用熟悉的編輯器撰寫程式，再推送到雲端。它解決的核心痛點是：線上編輯器沒有版本控制、沒有型別提示、無法搭配既有的 Git 工作流。

它透過 Apps Script API 與雲端專案雙向同步，本機的 .gs / .ts 檔案與線上專案一一對應。你寫的還是 GAS，只是開發體驗變成標準的前端工程流程。

前提

需要 Node.js 環境。B Team 既有的 clasp 專案都採這套流程，接手既有專案時同樣適用。

兩種專案型態

開始前必須先分清楚你要做的是哪一種，因為建立方式、觸發權限、綁定關係都不同。

Standalone

獨立 Script

  • 不依附任何檔案，獨立存在於 Drive
  • 適合：排程作業、Web App、Library、對外 API 串接
  • 可自由被多個專案共用
  • B Team 的 NotifyLib、EnvLib、Secrets 都屬這類

Container-bound

綁定容器（試算表/表單/簡報）

  • 依附在特定 Sheets / Forms / Slides 上
  • 適合：自訂選單、onEdit 觸發、直接操作當前檔案
  • 可用 SpreadsheetApp.getActiveSpreadsheet()
  • 隨容器複製、刪除，生命週期綁在一起
選型建議

若邏輯需要被多處重用或獨立排程，優先做 Standalone 再以 Library 引入；只有真正需要「操作這份試算表本身」（選單、儲存格觸發）時才用 bound。你既有的 worklog 報表系統就是 Standalone + Sheets API 操作，而非 bound。

前置需求

目前 clasp 已進入 3.x（截至 2026 年 3 月為 3.3.0），與舊教學常見的 2.x 有幾項對環境設定影響很大的差異，務必先看清楚。

項目要求 / 變化
Node.js3.x 要求 ≥ 22.0.0（舊 2.x 只要 ≥ 12，別照舊教學）
套件管理透過 npm 全域安裝；無官方 Homebrew formula
TypeScript3.x 不再內建轉譯 TS，需自備 bundler（Rollup 等）
Apps Script API全帳號一次性開啟（下方步驟）
TS 專案注意

你既有專案若靠 clasp 直接 push .ts，升到 3.x 會失效。改用社群 template（如 apps-script-engine-template）以 Rollup 打包成 .gs 再 push，或維持 .gs + @types/google-apps-script 型別提示的寫法。

安裝 clasp

核心觀念先講清楚：clasp 本身沒有 brew formula，brew 的角色是幫你裝 Node.js，clasp 一律走 npm。所以「brew 方案」實際上是「用 brew 準備 Node 環境，再 npm 裝 clasp」。以下三種擇一取得 Node。

macOS · Homebrew

# 裝 Node（含 npm）
brew install node

# 或用 nvm 管多版本
brew install nvm

跨平台 · nvm

# 裝並切到 22
nvm install 22
nvm use 22

官方安裝檔

到 nodejs.org 下載 LTS（≥ 22）安裝檔，npm 會一併裝好。

確認 Node 版本達標

node -v   # 需 >= 22.0.0
npm -v

全域安裝 clasp

# brew 裝的 Node 不需 sudo，避免權限問題
npm install -g @google/clasp

# 驗證
clasp --version   # 應為 3.x
brew 裝 Node 的好處

全域 npm 目錄在使用者權限下，npm install -g 不必 sudo，省掉 EACCES 權限錯誤。這也是團隊 onboarding 建議路徑。

開啟 Apps Script API

到 script.google.com/home/usersettings 把「Google Apps Script API」開啟。全帳號一次性設定，忘了開會在 push 時報 User has not enabled the Apps Script API。

登入方式

先回答你的問題：clasp 沒有 SSH 登入。它走的是 Google OAuth，不是 SSH 金鑰。你想問的「SSH 進遠端主機後怎麼登入」屬於「無瀏覽器環境」情境，用下面的 --no-localhost 解決；若是完全自動化（CI、service account）則用 --adc 或憑證檔還原。

1. 一般互動登入

# 開瀏覽器完成 OAuth 授權
clasp login

憑證存到全域 ~/.clasprc.json，之後所有專案共用。此檔是敏感檔案，絕不進版控。

2. 無瀏覽器 / SSH 遠端主機 你的情境

# 不起本機伺服器，手動貼授權碼
clasp login --no-localhost

# 3.x 可指定 redirect 埠，對應自訂 OAuth client 設定
clasp login --no-localhost --redirect-port 8888

流程：clasp 印出授權 URL → 你在任何能開瀏覽器的裝置上開啟並授權 → 把回傳的碼貼回 SSH 終端機。這就是透過 SSH 連進遠端 build 機時的標準做法。

3. 多帳號切換

# 具名憑證，例如公司帳號與測試帳號分開
clasp login --user work
clasp login --user testbot

# 執行時指定身分
clasp run-function --user testbot myFunction

4. 自動化 / CI（取代 service account 心智）

# 方式 A：自帶 OAuth client（Desktop App 類型）憑證檔
clasp login --creds creds.json

# 方式 B：讀環境的 Application Default Credentials
clasp <command> --adc
CI 憑證還原

GitHub Actions 上跑 clasp push，把本機 ~/.clasprc.json 內容存成 repo secret，workflow 開頭還原成檔案再執行——與你 Jira-to-GitHub 同步用 PAT 的「機密進 secret、執行期還原、用完不落地」模式一致。--adc 則適合已在 GCP 環境、用 workload identity 的情境。

情境指令
本機日常開發clasp login
SSH 進遠端主機、無瀏覽器clasp login --no-localhost
多帳號clasp login --user <name>
CI 自動部署secret 還原 .clasprc.json 或 --adc

設定檔解析

clasp 專案由兩個檔案控制，理解它們是掌握整套流程的關鍵。

檔案作用進版控？
.clasp.json綁定本機與雲端專案的 scriptId、根目錄可以（不含機密）
appsscript.json資訊清單：時區、相依 Library、Web App 權限、OAuth scope是
~/.clasprc.json你的登入憑證絕對不要

.clasp.json 範例

{
  "scriptId": "1a2B3c4D...雲端專案ID",
  "rootDir": "./src"
}

rootDir 指定原始碼資料夾，讓你把 .gs 集中在 src/，把設定檔、README、.gitignore 留在專案根目錄，是乾淨架構的第一步。

appsscript.json 範例

{
  "timeZone": "Asia/Taipei",
  "dependencies": {
    "libraries": [{
      "userSymbol": "NotifyLib",
      "libraryId": "...libraryScriptId",
      "version": "5"
    }]
  },
  "exceptionLogging": "STACKDRIVER",
  "runtimeVersion": "V8"
}

獨立 Script Standalone

兩種起手式：從零新建，或接手雲端既有專案。

A. 從零新建

mkdir my-scheduler && cd my-scheduler

# type 指定 standalone
clasp create --type standalone --title "月報排程" --rootDir ./src

執行後會產生 .clasp.json 與 src/appsscript.json，同時在你的 Drive 建立一個獨立專案。

B. 拉取雲端既有專案

# 從線上編輯器網址列取得 scriptId
clasp clone "1a2B3c4D...scriptId" --rootDir ./src
Library 的做法

Library 本質就是 Standalone。開發完成後在線上編輯器「部署 → 新增部署作業 → 類型選程式庫」，取得 scriptId 給使用端在 appsscript.json 引入即可，如上面 NotifyLib 的範例。

綁定試算表 Container-bound

bound 專案的關鍵限制：clasp 無法直接為既有試算表建立綁定專案。clasp create --type sheets 會「新建一份試算表」並綁上 script。分兩種情境處理。

情境 A：全新試算表 + 綁定 script

mkdir sheet-tool && cd sheet-tool

# 會新建一份 Sheets，並回傳試算表與 script 兩個 URL
clasp create --type sheets --title "B Team 工時表" --rootDir ./src

情境 B：既有試算表要接 clasp（常見）

你手上已有一份試算表，想把它的綁定 script 納入本機開發：

打開試算表 → 擴充功能 → Apps Script，開啟綁定的 script 編輯器。

在編輯器 專案設定 頁複製 指令碼 ID（scriptId）。

本機用 clone 把它拉下來：

clasp clone "該bound專案的scriptId" --rootDir ./src
辨識重點

bound 專案在 clasp clone 之後，用法與 standalone 完全相同（一樣 push / pull）。差別只在它的 scriptId 屬於某份容器，且程式能呼叫 getActiveSpreadsheet() 這類容器 API。你無法把 standalone 事後「轉」成 bound。

bound 專屬的 onOpen 選單範例

function onOpen() {
  SpreadsheetApp.getUi()
    .createMenu('B Team 工具')
    .addItem('產生月報', 'generateReport')
    .addToUi();
}

日常開發流程

指令用途
clasp push本機 → 雲端（開發主動作）
clasp push --watch存檔即自動推送，開發時常駐
clasp pull雲端 → 本機（同步他人在線上的修改）
clasp open用瀏覽器開啟雲端專案
clasp run <fn>從 CLI 執行雲端函式（需額外設定）
clasp deploy建立正式部署（Web App / Library 版本）
clasp logs查看執行日誌
push 會覆蓋

clasp push 是以本機為準覆蓋雲端。若團隊有人直接在線上改過，先 pull 或用 Git 合併，避免蓋掉他人變更。這也是為什麼要把 clasp 綁進 Git。

檔案架構設計

GAS 執行時所有 .gs 檔共享同一個全域命名空間，檔名只影響載入順序（字母序）。因此架構設計靠的是職責分層與命名約定，而非模組系統。以你既有的 worklog 系統為例，建議這樣組織：

worklog-report/
├── src/
│   ├── appsscript.json   # 資訊清單
│   ├── Config.gs        # 常數、環境設定（最先載入）
│   ├── JiraClient.gs    # 資料來源層：外部 API 封裝
│   ├── WorklogFetcher.gs # 領域邏輯：抓取與正規化
│   ├── SheetWriter.gs   # 輸出層：寫入 Sheets
│   └── Main.gs         # 進入點與觸發器
├── .clasp.json          # rootDir 指向 ./src
├── .claspignore        # 排除不推送的檔案
├── .gitignore
└── README.md

用命名空間物件避免污染

既然全域共享，用 IIFE 或物件字面把每個「模組」包起來，是你在 v2 bug triage 系統採過的做法，可沿用：

// JiraClient.gs
const JiraClient = (function() {
  function fetchWorklogs(jql) { /* ... */ }
  return { fetchWorklogs };
})();

// Main.gs 呼叫時語意清楚，不怕撞名
const logs = JiraClient.fetchWorklogs(query);

載入順序：用 Config 命名確保先行

因為是字母序載入，把設定放 Config.gs（C 開頭多半夠早）；若有嚴格相依，可用數字前綴如 00_Config.gs、10_Client.gs 明確控制順序。

.claspignore 範例

# 只推送 src 內的原始碼
**/**
!appsscript.json
!*.gs
!*.js

版本控制整合

把 clasp 綁進 Git 是這套流程最大的價值。你已在多個 GAS 專案採 clasp + GitHub，重點在 .gitignore 別漏了機密。

必備 .gitignore

# clasp 憑證絕不進版控
.clasprc.json
node_modules/

# .clasp.json 可進版控（只含 scriptId），
# 但若 scriptId 視為敏感，可改用 .clasp.json.example
機密管理

Jira / GitHub 憑證絕不寫死在 .gs。延續你的做法：用 PropertiesService.getScriptProperties() 存取，或抽成獨立的 Secrets Library（singleton），版控裡只留讀取邏輯不留值。

建議的 CI 心智模型

GitHub Actions 上跑 clasp push 需要把 ~/.clasprc.json 內容存成 repo secret，於 workflow 還原成檔案後再執行。這與你 Jira-to-GitHub 同步用 Fine-grained PAT 的憑證還原模式一致：機密進 secret，執行期還原，用完不落地。

常見陷阱

症狀原因與解法
push 報 User has not enabled the Apps Script API沒開 API，回 usersettings 開啟後重試
函式撞名、變數被覆蓋全域命名空間污染 → 改用命名空間物件包裝
bound 專案 getActiveSpreadsheet() 回 null從觸發器/選單以外的入口跑，取不到容器；改用 openById()
Library 改了但使用端沒生效Library 走版本號；改完要「新增部署版本」，使用端更新 version
push 覆蓋掉線上他人修改先 pull 或建立 Git 流程，禁止直接線上編輯
誤把 .clasprc.json 推上 GitHub立即撤銷憑證重新 clasp login，並加進 .gitignore
一句話總結

重用邏輯做 Standalone 並抽 Library；要操作特定檔案才做 bound；一律 clone 進本機、綁 Git、機密進 Properties 或 secret。剩下的就是標準前端工程流程。
